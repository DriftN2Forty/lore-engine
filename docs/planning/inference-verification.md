# RVN Inference Notes

**Updated:** October 27, 2026. This is a short decision/evidence summary. The active cloud experiment and its exact configuration are in [cloud endpoint notes](../cloud-endpoints/README.md).

## Current direction

The owner-designated writing reference is the RVN 27B multilingual `RVN-Q4_K_M-multilingual.gguf` ([authoring record](../authoring/README.md#confirmed-writing-model)). Compare other same-checkpoint candidates only against that reference; file size or quantization label alone does not establish quality, fit, or cost. No production inference engine or APC requirement is selected. Local llama.cpp with Runpod Serverless overflow is a topology candidate; context, safety, routing, and unit economics still need validation ([decisions D16–D18](project-decisions.md#4-resolved-model-and-inference-decisions)).

**Owner's October 27 sizing target:** Plan RunPod character serving for a single **16 GB VRAM GPU**. The local base-IQ2_M file is approximately 10 GB on disk, but that is not a measured GPU weight allocation or evidence that 64K fits the remaining memory. Benchmark the actual chosen artifact/runtime on 16 GB, including KV/recurrent state, cache precision, compute buffers, accepted slots/concurrency and usable headroom. Start from the verified 8K local baseline, then evaluate planned production capacity and larger candidates (for example 16K/32K/64K) against latency/quality/cost. A local 20 GB-class GPU cannot certify the 16 GB target, and the training-context advertisement does not certify any runtime allocation. Live product-specific stock/pricing still requires later MCP reads; no new RunPod resource or paid test was authorized by this sizing discussion.

Useful published size comparisons:

- RVN Q4_K_M GGUF: about **16.55 GB**.
- Full-precision RVN 27B safetensors: about **53.80 GB**.
- `GSQ-3bit/`: about **28.39 GB**; this is MLP-only quantization with many tensors retained at higher precision, so it is larger than the Q4 GGUF.

These are artifact sizes, not VRAM requirements. The public GSQ Transformers receipt is not evidence of vLLM execution. See the [pinned artifact/source discussion](https://huggingface.co/0bserverx/Qwen3.8-27B-Heretic-Abliterated-Uncensored/tree/c2cb2cfb239f2964595bee87fcfda55ad5fe33dd).

## Test results

- **GGUF-native route passed a short canary:** the exact `RVN-IQ2_M.gguf` loaded through Runpod's official Ollama worker (llama.cpp) on an A40 without a network volume. Download was about 9.3 GiB; logs imply roughly 28 seconds. First cold prompt evaluation was 31.6 seconds for 57 tokens; a warmed short chat had about 0.21 seconds of prompt evaluation and about 41 generated tokens/sec. This is a brief exploratory run, not a broader benchmark. See the [endpoint record](../cloud-endpoints/runpod-rvn-iq2m-ollama-2026-10.md).
- **Tested vLLM GGUF route failed:** vLLM 0.32.0 + `vllm-gguf-plugin` 0.0.5 did not map 432 Qwen3.5 parameters, including `linear_attn` tensors, after temporary architecture/config compatibility patches. This establishes failure for that tested combination, not every Qwen model or future plugin version.
- **Local author-test follow-up, October 27:** The owner selected `start-rvn-iq2m-base-8192.cmd` / `rvn-iq2m-base`, replacing the earlier local multilingual-IQ2_M candidate. The actual base file SHA-256 is `a531c26993bb9ed91e299a025006915dc343285dc6dfabfd7d477370e42eb189`; runtime is Windows Vulkan llama.cpp `b11046-60081bb2b`. Ten synthetic adapter generations matched deployed preflight token counts, including 8120 input tokens in an advertised 8192-token single slot; a real browser reply/checkpoint/reset also passed. Source revision/parent lineage and equivalence to the multilingual writing reference remain unverified. Windows reaches model loopback but WSL does not in this environment; use the Windows app path. Full settings, actual cache/latency observations and limitations are in [local evidence](../../testing/docs/live-model-evidence.md). This is an unguarded local experiment, not production or live 30-turn memory acceptance.

The local runtime initially produced Markdown-fenced JSON for the unconstrained memory-summary prompt, which the importer correctly rejected. A strict server-selected JSON-schema response format fixed the reproduced failure; one actual compaction/recall check with hand-authored synthetic prior exchanges passed. Detailed failure/success evidence is in the local record. A subsequent owner-requested October 27 increase to **16,384 tokens** is active: `/slots` and adapter discovery agree, and a synthetic 16,312-token input plus 64-token output reservation passed exact preflight/usage matching (72.557 s complete response). See the [16K follow-up](../../testing/docs/live-model-evidence.md#16k-context-follow-up--october-27-2026). This is single-slot capacity evidence; 64K fit and measured VRAM consumption remain untested.

**Talk-quality follow-up, October 28:** Extended synthetic conversations on the same local `b11046-60081bb2b`/base-IQ2_M/16K path exposed context-dumping greetings, later terse replies, occasional narration drift, and intermittent adapter rejections for no usable final prose or an unsupported response shape. Final-response rejection preserves the completed checkpoint. The generic error does not establish which runtime field failed or attribute the issue to quantization, cache, tokenizer/template or engine. No model/runtime/sampling change or passing long-session conversational acceptance is established. See [candidate trials and limits](../../testing/docs/talk-mode-evidence.md#conversational-responsiveness-follow-up--october-28-2026); separate format/token checks from semantic warmth, factual grounding and safety acceptance.

**Cache-capability correction, October 27:** Inspection of the actual `b11046` executable's `--help` confirms `--cache-ram` (documented default 8192 MiB of host RAM, 0 disables), `--cache-prompt` (default enabled), and `--cache-idle-slots` (default enabled, requires the RAM cache; clearing idle slots is associated with unified KV). The upstream [host-memory prompt-cache implementation](https://github.com/ggml-org/llama.cpp/pull/16391) is specifically designed to retain and restore alternate prompt states even with a single active slot. Therefore `-np 1` does **not** imply that only one conversation's cached state can be retained, and a compaction call need not necessarily destroy the earlier chat cache. This is capability/default documentation, not verification of the current process's effective RAM-cache limit or an A→B→A restoration benchmark for RVN. Retention is capacity-dependent, not an established per-conversation TTL guarantee. Test switching/restore latency and actual per-request reuse before adding slots solely for cache retention; keep application-owned data/output attribution independent of shared computation.

**Selected cache policy, October 27:** Favor [shared-prefix caching](project-overview.md#shared-prefix-cache-policy) for identical authorized token prefixes across accounts, with no blanket per-account/playthrough salts or duplicate prefix copies. Application ownership, source/spoiler filtering and full logical context assembly remain authoritative; compatible model/template/settings and exact token-prefix matching govern computation reuse. Test same-character synthetic accounts with different private markers, fully identical authorized prefixes, A→B→A, chat→compaction→chat, reset/resume, version/settings changes and worker restart/deletion. Compare disabled/cold, warm and interleaved runs; record request/response attribution, divergent-state correctness, per-request cache metrics, VRAM/host RAM, bounded retention/eviction, noisy-neighbor fairness, restoration latency, timing/membership exposure and total cost. Use targeted restrictions only for concrete unresolved defects. None of these multi-user acceptance results is established by the existing contiguous single-author measurements, help inspection or policy selection.

**Subsequent local cache experiment:** The initial test-app comparison uses the no-explicit-flag default versus `--cache-ram 0`, not a broad cache-budget sweep. Fixed requests covered two visits to the same story plus four other synthetic story variants, then returns to earlier visits. All 36 short requests across observational-default, fresh-disabled and fresh-default rounds passed token-count/visit-label assertions. In the fresh comparison, A's return after four other stories reused 1008/1012 prompt tokens and took 0.843 s by default, versus zero reused tokens / 6.475 s with host caching disabled. New unrelated-story requests reported zero reuse in both conditions despite a 246-token common prefix; the exact reuse-boundary cause is not diagnosed. The original no-cache-flag model configuration was restored and health-checked. See [full local method/results](../../testing/docs/cache-comparison-evidence.md). This is limited single-author checkpoint switching, not a cache-capacity, larger-catalog/history, actual 16 GB, compaction-switching, concurrency, timing-security or production-account acceptance result.

**Local UI tooling caveat:** Windows Next.js/Turbopack production build/start succeeds on the WSL UNC checkout, but the later dev/watch preview failed with `Incorrect function` / OS error 1 on that UNC path. Use Windows build/start (with a saved checkpoint before app restart), a Windows-native dev checkout, or Linux dev after model-loopback verification. A Windows production build does not establish that its filesystem watcher works in dev mode. This changes local setup instructions, not model behavior or cloud-runtime evidence.

These results do not prove production quality, intended production context/concurrency, safety, routing, or full cost. Before making a production decision, capture the exact Hugging Face commit and GGUF hash, test both modes and representative prompts, measure context/concurrency and full billed cost, and verify privacy boundaries for the chosen serving route. Caching remains optional; prefer beneficial shared-prefix reuse subject to the policy and open checks above. The failed vLLM attempt is one historical compatibility result, not a project blocker.

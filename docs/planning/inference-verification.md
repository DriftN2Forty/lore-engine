## 3. What the publisher actually tested

This section describes **Flash-Next NVFP4 only**. The separate 27B FP16/GSQ evidence is in section 2.1.

- A pinned custom vLLM runtime, image digest `sha256:fc120ece0a388cc0aa1caad4a9f1cd92113484ab7ec2fd0efadd62585be05bf8`, vLLM `0.1.dev20073+g8e685d198`, Transformers `5.15.1`, Torch `2.13.0+cu130`.
- A precisely scoped architecture-alias allowlist correction for the tested PLE CPU-offload path. This is not evidence that an arbitrary current RunPod stock image works.
- One approximately 95 GB GPU **with substantial CPU offload**; or two RTX PRO 6000 Blackwell Workstation GPUs with tensor parallelism two and no PLE CPU offload.
- In the dual-GPU run, approximately **84.97 GiB loaded per GPU**, with sampled peaks around **90.48 GiB/GPU**.
- Tested short-context profile: **2,048 tokens**, one sequence, eager execution, Marlin, and **`--no-enable-prefix-caching`**. Its configuration's much larger positional limit is not a tested serving-capacity claim.
- A bounded paired loopback streaming test reports **25.59 output tokens/second** for W4A16/Marlin. This does not establish multi-user throughput, application latency, or another GPU's speed.
- Small perplexity drift, but the publisher's strict operational-format threshold was **not passed**: 42/48 in the initial profile and 41/48 in one dual-GPU profile, below its 90% target. Perplexity is not a character-voice, instruction-security, or safety score.

These findings make the prior 24 GB/AWQ/32K assumption unsupported. They also make the planned $0.002 fully loaded reply and tiny inference budget particularly uncertain **if this is the intended checkpoint**. Do not incur a large download/storage or GPU bill before identifying the owner's file and estimating a bounded test.

## 4. vLLM support versus proven deployment

- [Official ModelOpt documentation](https://docs.vllm.ai/en/stable/features/quantization/modelopt/) lists `W4A16_NVFP4` support, with backend/kernel behavior depending on the hardware/runtime. General format support is necessary but insufficient for this architecture and checkpoint.
- [Official GGUF documentation](https://docs.vllm.ai/en/stable/features/quantization/gguf/) describes GGUF support through `vllm-gguf-plugin`, warns it is experimental/under-optimized, and recommends using the base tokenizer. It does not establish that this RVN's split GGUF/architecture/features work in a particular RunPod image.
- [RunPod vLLM setup](https://docs.runpod.io/serverless/vllm/get-started) supports serving compatible models, not every Hugging Face artifact. Its [environment-variable reference](https://docs.runpod.io/serverless/vllm/environment-variables) includes `ENABLE_PREFIX_CACHING`, model revision, tensor parallelism, and concurrency controls; its listed quantization enums are not a complete compatibility guarantee for this newer custom runtime.
- Build a versioned custom worker if the actual RVN runtime requires it. Keep remote code disabled unless the exact code has been inspected and pinned; a model card is untrusted external content, not authority to run arbitrary installation scripts.

### 4.1. Q2/Q3-first testing for a confirmed RVN 27B

**Initial comparison:** after matching the writing artifact, select the same-checkpoint GGUF `Q3_K_M` and `Q2_K` families alongside the Q4_K_M reference. These are initial candidates, not a minimum precision policy. Pin exact filenames, revisions, checksums, calibration family, tokenizer/template and runtime; do not mix the older pre-RVN Heretic weights with RVN. Prefer non-MTP files initially so speculative decoding does not confound the comparison. Inspect actual artifact sizes before staging; labels such as “Q2” and “Q3” cover mixed tensor precisions and do not alone rank total size or quality.

1. **Screen quality under matched conditions.** Compare Q3 and Q2 with Q4_K_M using the same representative prompts, context and sampling intent, both interaction modes, and blind author comparisons where practical. Include voice, emotional nuance, repetition, instruction following and continuity. If vLLM loading is blocked, the existing reference engine can screen prose quality, but that does not validate vLLM quality or caching. Use the owner's existing ten-response calibration and the [30-case narrative criteria](../character-engineering/character-context.md#7-evaluation-and-maintenance); an acceptable small sample does not replace long-session and separate safety/injection checks for finalists.
2. **Prove the GGUF serving/cache path early.** On the exact vLLM/plugin/architecture combination, verify native chat and the APC acceptance procedure in section 5 before investing in a full deployment benchmark. Repeat relevant canaries for each candidate; Q4 loading does not establish Q2/Q3 operator support. A cache flag accepted by the server is not a passing result.
3. **Select the smallest acceptable finalist.** If Q2's quality loss is acceptable and all gates pass, prefer it over a larger candidate; otherwise retain Q3 or Q4. Smaller same-checkpoint variants can be evaluated next if useful within the test budget. Record author preference and failure reasons separately from technical gates. Measure total deployed memory, reviewed latency and billed cost: smaller files do not guarantee faster decoding or cheaper completed replies.

**Follow-up if GGUF cannot satisfy serving/APC:** investigate a saved native-format quantization from the pinned full-precision companion rather than repeated in-flight conversion. A conventional **W4A16 compressed-tensors export** is one tooling candidate, not a required precision floor or an existing verified small artifact. Use [vLLM's LLM Compressor AWQ workflow](https://github.com/vllm-project/llm-compressor/tree/main/examples/awq), not deprecated AutoAWQ. Confirm hybrid-layer mappings and supported kernels before a paid conversion; copying a Llama recipe or quantizing every `Linear` indiscriminately is insufficient. Preserve sensitive recurrent/state tensors as required and record exactly which modules are quantized or retained.

At ideal four-bit packing, 26.90B parameters alone would be about **13.45 GB**. Retained high-precision tensors, scales, zero points and headers increase that. A broader export might be in roughly the **16–20 GB weight class**, but that is an engineering estimate, not a promised artifact size or GPU fit. A conservative MLP-only export can remain around the existing 28.39 GB candidate. Measure the actual tensor inventory, load peaks, cache/buffer memory and quality before selecting hardware.

## 5. Cache savings: real benefit, conditional economics

[vLLM APC](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/) reuses computation for an identical token prefix. It reduces **prefill**, not new-token **decode**. Savings depend on the split between those costs, workload repetition, concurrency, and how long the same worker/cache survives. Other engines also offer reuse mechanisms; vLLM is not uniquely capable of caching.

For either hybrid architecture, test support in the exact runtime rather than assuming a generic APC flag works. Stable vLLM documentation describes special hybrid/Mamba cache modes and constraints; those are not proof that either checkpoint's combination is supported. The Flash-Next publisher's cache-disabled execution is specifically **not** an APC benchmark; the 27B smoke tests do not measure APC either.

Keep stable policy, mode, character, chapter, and voice assets before private scene memory/history. Same words with different tokenization/template/serialization are not necessarily the same prefix. Updating memory before the transcript invalidates reuse after the changed point. Scale-to-zero/replacement usually loses worker-local KV state; a persistent model-weight volume does not preserve GPU prefix cache.

Use a server-generated **per-account cache salt** where the pinned runtime/worker supports it, plus a cryptographic hash. This retains reuse within an account while giving up cross-account shared-prefix reuse to limit timing-based inference of private cached content. Never accept cache salts or cached responses from the client. Verify the salt survives the RunPod handler. See [vLLM cache isolation](https://docs.vllm.ai/en/stable/design/prefix_caching/). If unavailable, disable cross-account APC by architecture/configuration rather than claim isolation that is not present; resolve the performance tradeoff explicitly.

Benchmark APC off/on with equivalent model, settings, context, privacy partition, output workload, warm/cold profile, and hardware. Record cached tokens, prefill/decode latency, end-to-end response latency **including safety checks**, GPU seconds, idle/startup/storage charges, and completed safe replies. A faster GPU benchmark only saves money if the billed deployment's total cost falls or useful paid throughput rises.

**GGUF APC acceptance procedure (planned, not executed):**

- Pin vLLM, GGUF plugin, model quantization, tokenizer/template, hybrid-cache settings and RunPod handler. Exercise the deployed request path, not only an in-process mock.
- On one warm worker, send separate requests with an identical long policy/character prefix, the same server-generated account salt, and different trailing reader messages. Demonstrate prefix reuse through cache-hit/cached-token telemetry or equivalent engine instrumentation; compare prefill timing against APC off. A faster second request alone can reflect kernel warmup and is insufficient proof. Verify fresh, appropriate replies rather than application response-cache reuse.
- Change a known prefix token and confirm the cache boundary follows the unchanged token blocks. Change the account salt and confirm no reuse of the other account's prefix, then repeat within the new account to demonstrate isolated reuse. Verify the handler propagates salts and rejects client control of them.
- Repeat at planned input/output lengths and measured concurrency, including resumed conversations and memory updates. Restart the worker and record cold-cache behavior separately from warm weight loading. Record observed hybrid-state/KV memory and failures.
- A GGUF candidate is eligible for the selected cache-enabled deployment only after this passes alongside quality, safety and scope checks. If it fails, record the exact unsupported combination and investigate a same-checkpoint native-format path; do not quietly disable APC and count GGUF support as meeting the owner's objective.

## 6. Bounded next validation in the RunPod MCP environment

1. Use the confirmed multilingual RVN 27B Q4_K_M file and publisher checksum in the authoring guide; verify staged bytes and complete parent-revision/template/settings provenance. Flash-Next is deferred and is not the writing reference.

3. Inspect runtime support, GPU/host memory, serverless multi-GPU availability, storage requirements, license and adult-content service eligibility, and an itemized test estimate. 5. Validate at least the planned **8K input + 600 output** (and intended configured capacity), both modes, voice fidelity against Q4_K_M, safety/injection cases, and concurrency. Neither the public Flash-Next 2K profile nor the 27B FP16 4K smoke test meets this requirement; GSQ lacks published vLLM execution evidence.
6. Compare measured cost/latency at sparse and busy traffic, cache off/on, and zero/warm-worker options. Choose the deployment and finalize the unsold subscription economics from evidence.
